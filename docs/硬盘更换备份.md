# 硬盘更换与备份(btrfs + ESP 双盘迁移指南)

> **结论先行**:换盘 = **快照 send/receive 迁数据 + 引导身份去重 + 切换检查清单**,三步缺一不可。最大的暗雷不是数据,而是 **ESP 的身份标识**——dd 克隆会把 ESP 的分区 GUID 和 FAT 卷 ID 一起复制,双盘同插时固件和挂载全靠这些标识寻址,**随机命中其中任何一块**:升级时内核写入 A 盘、重启时固件却引导 B 盘上的旧内核,内核与 `/lib/modules` 版本错位,系统直接进 emergency。

本文适用:Linux + btrfs 子卷布局(`/@`、`/@home` 等)+ UEFI 引导,新旧双盘同插过渡的场景。无论用 GRUB、systemd-boot 还是 Limine,道理相同。

## 一、为什么不能 dd 整盘克隆

1. **活机 dd 挂载中的 btrfs 必撕裂**:journald、snapper 定时器总会写入,克隆副本的 transid 落后于实际元数据,`btrfs check` 直接打不开(`parent transid verify failed`)。
2. **停掉写入源不可靠**:SIGSTOP journald 后 systemd 会把停住的进程杀掉重启,静默窗口只有几十秒。
3. **ESP 身份被连锅端**(最致命,见第三节):GPT 分区 GUID、FAT 卷 ID、引导器配置一起复制,双盘即刻"人格分裂"。
4. **文件系统 UUID 冲突**:`btrfstune -U` 在源盘仍挂载时拒绝执行(`fsid is not unique`),善后很被动。

## 二、正解:原子快照 + btrfs send/receive

### 1. 新盘准备

```bash
# ESP + btrfs 两分区(示例,parted/sgdisk/gdisk 均可)
sgdisk -n 1:0:+1G -t 1:ef00 -n 2:0:0 -t 2:8300 /dev/nvmeXn1
mkfs.fat -F32 /dev/nvmeXn1p1

# 新文件系统 → 全新 fs UUID,不与旧盘冲突
mkfs.btrfs /dev/nvmeXn1p2
mount /dev/nvmeXn1p2 /mnt/new
```

### 2. 逐子卷迁移

```bash
# 旧盘侧:每个子卷先做只读原子快照,再发送
btrfs subvolume snapshot -r /              /.snapshots/mig-root
btrfs subvolume snapshot -r /home          /.snapshots/mig-home
# ……其余子卷同理(@log @cache @srv 等)

btrfs send /.snapshots/mig-root     | btrfs receive /mnt/new/__root__
btrfs send /.snapshots/mig-home     | btrfs receive /mnt/new/__home__
```

数据量大时 `send | receive` 之间可加压缩/走 SSH 跨机。receive 端的子卷名可以直接建成目标名(如 `/mnt/new/@`),不必事后改名。

### 3. 子卷翻可写

receive 出来的子卷带 `received_uuid` 且默认只读:

```bash
for s in @ @home @log @cache; do
    btrfs property set -ts /mnt/new/$s ro false
done
```

### 4. swapfile(如有)

swapfile 必须在独立子卷上建并 NOCOW,否则快照/平衡会毁掉它:

```bash
btrfs subvolume create /mnt/new/@swap
truncate -s 0 /mnt/new/@swap/swapfile
chattr +C /mnt/new/@swap/swapfile
dd if=/dev/zero of=/mnt/new/@swap/swapfile bs=1M count=20480 status=progress
chmod 600 /mnt/new/@swap/swapfile
mkswap /mnt/new/@swap/swapfile
btrfs inspect-map-swapfile /mnt/new/@swap/swapfile   # 拿到物理 offset,填进 cmdline resume_offset
```

注意:`resume_offset` 是**文件物理偏移**,换盘重建 swapfile 后必须重新查,旧值作废。

### 5. 改 fstab 与引导配置

- 新盘系统副本内的 `/etc/fstab`:所有旧 fs UUID 批量替换为新 fs UUID
- 引导器配置(GRUB 的 `grub.cfg`/`custom.cfg`、Limine 的 `limine.conf`、systemd-boot 的 entries):`root=UUID=`、`resume=UUID=`、`rootflags=subvol=` 全部核对
- **改的是新盘副本里的文件**——旧盘上正在运行的系统一个字都不用动,这是快照迁移天然的优势

### 6. 处理 ESP(关键,见下节)

## 三、ESP 身份去重:双盘共存的生命线

### 机理

UEFI 固件的启动项按 **GPT 分区 GUID** 定位 ESP(`HD(1,GPT,<partuuid>)/\EFI\...`);Linux 挂载 `/boot` 按 **FAT 卷 ID**(`UUID=XXXX-XXXX`)寻址。**任何一个重复,行为都是"碰运气"**:

- 固件每次重启从枚举顺序碰上的第一个同 GUID 分区引导 → 每次可能不同盘
- `mount /boot` 挂到任意一个同卷 ID 的 ESP → 升级内核可能写错盘

两个标识都重复时,典型事故链:**升级内核 → `/boot` 挂到 A 盘,新内核写 A 盘 → 重启 → 固件引到 B 盘 ESP 上的旧内核 → 根分区里只剩新版本模块 → `modprobe` 全部失败 → `/boot` 挂载报"未知的文件系统类型 vfat" → emergency**。

> nvme 设备名(nvme0/nvme1)本身每次启动也可能翻转,别拿它当稳定标识;一切以 UUID/GUID/序列号为准。

### 处理方式(二选一)

**方式 A(推荐):新盘 ESP 重建**,不克隆:

```bash
mkfs.fat -F32 /dev/nvmeXn1p1        # 全新卷 ID
mount /dev/nvmeXn1p1 /mnt/new/@/boot
# 重装引导器:grub-install / systemd-boot / limine-entry-tool 等
# 内核文件与配置由 pacman 钩子/引导器工具重新生成
```

**方式 B:克隆旧 ESP 但立即改身份**(想保留引导器配置和历史内核时):

```bash
# 改 FAT 卷 ID(mtools,十六进制 8 位)
mlabel -N 1A2B-3C4D -i /dev/nvmeXn1p1 ::

# 改 GPT 分区 GUID
sgdisk --partition-guid="1:$(uuidgen)" /dev/nvmeXn1
```

### 验证(双盘同插时必做)

```bash
lsblk -o NAME,SIZE,PARTUUID,UUID          # 两盘 ESP 两个维度都不同
efibootmgr -v                             # 启动项的 GUID 唯一命中目标盘
ls -l /dev/disk/by-partuuid/<目标GUID>    # 恰好一个符号链接
```

## 四、切换与回退策略

**双盘并存期是最危险的状态**,要么尽快完成切换,要么明确回退,别长期"双主盘":

1. **切换**:BIOS 启动顺序指向新盘 ESP → 进新盘系统(核对 `findmnt /` 的来源)→ 跑一轮更新与快照基线
2. **回退**:旧盘自始至终保持可引导、未被改动,拔掉新盘(或改回启动顺序)即回退
3. **收尾**:新盘稳定运行一个更新周期后,再处理旧盘(擦除/降级为数据盘);此时记得旧盘 ESP 的引导文件已无意义,但**分区 GUID 若与新盘重复,处理旧盘时一并换掉**,别留给未来

## 五、故障排查速查(已进 emergency 怎么办)

| 症状 | 含义 | 排查 |
| --- | --- | --- |
| `mount: /boot: 未知的文件系统类型"vfat"` | vfat 只是背锅侠——**modprobe 失败**,内核模块加载不了 | 比对 `uname -r` 与 `/lib/modules/`;不一致 = 引导了错误 ESP 上的旧内核 |
| `Failed to initialize nft: Protocol not supported` | 同上,nftables 模块也加载不了 | 同上 |
| fsck/mount 每次报的设备名不同(nvme0↔nvme1 翻转) | 正常现象,但若 **UUID 相同**则是撞车信号 | `lsblk -o PARTUUID,UUID` 查两盘重复 |
| `Failed to mount /boot` → 进 emergency | local-fs 失败,UEFI 机上九成是 ESP 问题 | `journalctl -b -1 -u boot.mount` 看具体报错 |

定位思路:

```bash
journalctl --list-boots                      # 找到失败的启动序号
journalctl -b -1 | grep -iE 'failed|mount|emergency'   # 直接死因
```

**救援通道**:引导器的快照菜单(GRUB + grub-btrfs、Limine 的 limine-snapper-sync 等)可以从升级前快照引导,快照内模块与历史内核版本匹配即可进系统。注意此类引导多为**只读 overlay**,进去后对系统本身的改动重启即丢——只用来修引导,修完就正常重启。

## 六、换盘检查清单

复制走,逐项打勾:

- [ ] 新盘各子卷齐全、已翻 rw(`btrfs property set -ts … ro false`)
- [ ] 新系统 fstab 所有挂载点 UUID 已指向新 fs UUID
- [ ] 引导器 cmdline:`root=`/`resume=` 指向新 UUID,`subvol=` 正确
- [ ] swapfile 重建于 NOCOW 子卷,`resume_offset` 已按新文件重新查询
- [ ] ESP 与根内 `/lib/modules` **同一套内核版本**
- [ ] 双盘同插:两盘 ESP 的 **FAT 卷 ID 不同**、**分区 GUID 不同**
- [ ] `efibootmgr -v` 启动项唯一命中目标盘 ESP
- [ ] `journalctl -b 0 -u boot.mount` 无失败记录
- [ ] 旧盘原样保留至少一个更新周期,再考虑擦除
